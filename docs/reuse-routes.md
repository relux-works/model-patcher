# Reuse routes for targeted model-weight changes

**Sources checked: 6 November 2026.** Capability descriptions are supported by the cited primary sources; recommendations are inferences and unmeasured properties remain unknown.

The immediate goal is to deliver a small, targeted weight change for an exact GGUF model, with safetensors as a later route. The practical starting point is to reuse a producer that actually expresses the desired edit, then deliver and identify its result. None of the options below establishes that an arbitrary sparse coordinate edit can be safely or exactly applied to every GGUF. Their applicability, artifact size, memory, execution time and effects on model behavior are unmeasured here.

**Recommendation (inference):** first match the desired operation to a native GGUF editor. NeuronDump is worth inspecting when its documented scale, zero or embedding operations describe the change; it is not documented as a general arbitrary-coordinate replacement tool. For an already prepared exact target, compare ggufpacker's regeneration-based delivery with an ordinary byte delta and the whole file. ggufpacker is specifically a quant-regeneration packer, not a general patch for unrelated edited models. VCDIFF/xdelta remains a provisional candidate, not a selected winner. If the edit exists in a source BF16 model instead, preserve its source-specific provenance, prepare the GGUF target through an appropriate conversion, and treat the output as a separate exact artifact. For a real LoRA, use the compatible native adapter or export path rather than assuming it represents arbitrary exact replacements.

## Direct GGUF choices

**NeuronDump — edits with a particular meaning.** Its [intervention documentation](https://github.com/aymen94/NeuronDump/blob/c97010a62803e132f3bc2ffec65e7c22f40a6f91/docs/interventions.md) describes an importable/exportable edit stack and a bake operation writing a new GGUF. The documented operations include scaling or zeroing model components and scaling or replacing token embedding rows. It also describes activation patching, steering and sampling changes; these are not all weight edits. Bake reports runtime-only operations such as activation patching and steering as skipped, and writes sampling, system and template settings to a separate Modelfile. The [bake implementation](https://github.com/aymen94/NeuronDump/blob/c97010a62803e132f3bc2ffec65e7c22f40a6f91/crates/neurondump-core/src/edits/bake.rs) also records applied, skipped and re-encoded tensors. It converts scaled quantized tensors to Q8_0 when the row length permits and otherwise to F16; aligned zeroing has a separate path. Tied embeddings can produce a different input/output effect when baked than at runtime.

**Inference:** this is a real GGUF-native candidate for its supported operations, with potentially broader changes than a few exact coordinates. The documented edit vocabulary does not establish arbitrary indexed BF16 bit replacement on packed GGUF weights, exact preservation of neighboring values, or equivalence between runtime and baked behavior. Check operation coverage, tensor types, report, output identity and runtime compatibility for the actual model. No model has been edited or evaluated here.

**ggufpacker — regeneration and exact reconstruction.** Its [README](https://github.com/theadamdanielsson/ggufpacker/blob/8b13bcfedcbdb1548bfcb8c8021c2c5e0ec02d94/README.md) describes packs of GGUF quantizations derived from a high-precision GGUF source using `llama-quantize`. An EXACT plan uses a regeneration recipe; a NEAR plan adds a stored header and compressed XOR correction; a blob plan stores the whole file. The [packer](https://github.com/theadamdanielsson/ggufpacker/blob/8b13bcfedcbdb1548bfcb8c8021c2c5e0ec02d94/src/ggufpacker/packer.py) tests reconstruction against the original hash before recording a non-blob plan. The [delta code](https://github.com/theadamdanielsson/ggufpacker/blob/8b13bcfedcbdb1548bfcb8c8021c2c5e0ec02d94/src/ggufpacker/delta.py) requires congruent tensor layouts for the XOR data-region route, including padding; the [unpacker](https://github.com/theadamdanielsson/ggufpacker/blob/8b13bcfedcbdb1548bfcb8c8021c2c5e0ec02d94/src/ggufpacker/unpacker.py) verifies the reconstructed SHA-256 and removes a mismatching output.

The documentation scopes v0 packs to the quantizer build and machine context and says LoRA adapters and finetunes are outside its regeneration scope. The source and required quantization inputs and tools must be available; multi-shard files can fall back to blobs. A different quantizer binary produces a warning, while the final hash determines acceptance. **Inference:** a target generated as a compatible quantization may fit this route; a sparse edited GGUF is not thereby established as a supported compact correction against its original GGUF. The project reports reconstruction results for particular models and builds; those are author-reported outcomes, not measurements or portability guarantees for this use case.

## Other existing routes

**Exact byte delivery.** For a known base and a separately prepared target, [VCDIFF](https://www.rfc-editor.org/rfc/rfc3284) and [xdelta](https://github.com/jmacd/xdelta/releases/tag/v3.2.2) are generic byte-delta candidates; [zstd `--patch-from`](https://github.com/facebook/zstd/blob/v1.5.7/programs/zstd.1.md) is another. Neither expresses which weights changed. Record the exact codec, version and options and independently verify the entire source and target with SHA-256. Decoder support, interoperability, size and resource use remain unknown. A whole-target fallback avoids the base dependency, subject to distribution rights, and must identify the same target bytes. This route delivers a prepared result; it does not discover or produce the fix.

**Git-Theta — checkpoint history.** Its [README](https://github.com/r-three/git-theta/blob/65d6e2114d14af1eeed092965d1f141f5ef478e2/README.md) describes tracking parameter groups and dense, sparse and low-rank updates in Git, along with model merge mechanisms. Its [safetensors checkpoint plugin](https://github.com/r-three/git-theta/blob/65d6e2114d14af1eeed092965d1f141f5ef478e2/git_theta/checkpoints/safetensors_checkpoint.py) reads and writes through the safetensors NumPy API. **Inference:** it is relevant to later safetensors checkpoint history when its Git/LFS workflow and update semantics fit. The inspected sources do not establish native GGUF support, a compact arbitrary GGUF patch, byte-identical serialization, or a drop-in delivery path for the target use case. A group-level diff does not itself verify individual changes or model behavior.

**BLAZE-X — archive-level tensor diff.** Its [patch source](https://github.com/markndg/blazex/blob/10906f54c74a222a076cda6a6e8997888fb8a297/src/patch.rs) describes unchanged, modified, added and removed tensor entries, with a target archive header containing configuration, tokenizer and ordering; application also handles sidecars. Its [README](https://github.com/markndg/blazex/blob/10906f54c74a222a076cda6a6e8997888fb8a297/README.md) describes importing safetensors into its own archive, diffing archives, and exporting GGUF. This establishes a tensor-aware archive route, not direct patching of an existing GGUF file or byte-identical reproduction of a separately produced GGUF. The [codec terms](https://github.com/markndg/blazex/blob/10906f54c74a222a076cda6a6e8997888fb8a297/codec/README.md) state that the required prebuilt SplitStream library is proprietary and restrict its redistribution and use outside the BLAZE-X toolchain. Its suitability for reuse depends on those actual terms and the intended deployment. Author-reported patch results are not independently measured here.

**llama.cpp LoRA and export.** The [export documentation](https://github.com/ggml-org/llama.cpp/blob/6c01da6278ab6c69ed67d9124806b50d2b299ba7/tools/export-lora/README.md) describes applying multiple GGUF LoRA adapters with optional scales and exporting a merged model. In the pinned [implementation](https://github.com/ggml-org/llama.cpp/blob/6c01da6278ab6c69ed67d9124806b50d2b299ba7/tools/export-lora/export-lora.cpp), split base models and quantized LoRA tensors are rejected, and multiple adapters must have the same tensor list. For tensors affected by adapters, it converts non-F32 base data to F32 for merging; output types are F32 for F32, BF16 for BF16 and F16 otherwise. Unaffected tensors are copied in their original representation, while file metadata is marked mostly F16. Thus a quantized input does not imply the same packed quantized output. Adapter architecture checks do not establish full base identity or quality. Use compatible runtime adapter support when appropriate; export and runtime behavior must each be checked for the target version. A low-rank update is not an exact substitute for an arbitrary sparse replacement.

## Identity, quantization and evidence

A logical coordinate is not necessarily an offset in a GGUF file. Conversion can change tensor layout and quantization packs weights into blocks. For example, the [Q4_0 layout](https://github.com/ggml-org/ggml/blob/57e2c2ca2a7cae756b1c4dfafa0cdfef9051d234/src/ggml-common.h) shares a scale across 32 values. **Inference:** a small change may round away, while changing a block's scale or requantizing may change neighboring representations; the effect depends on the quantizer. Do not transplant a BF16 index into packed bytes without a verified mapping and operation. A successful hash check verifies designated bytes, not useful behavior or publisher identity.

For any delivery, identify every required source and target file by SHA-256 and size, the producer and relevant operation or conversion, and the decoder and profile. Bind runtime, tokenizer and evaluation context separately. Two deltas from the same base do not automatically compose; use an explicitly ordered chain with each intermediate identity or a separately prepared combined target. Overlapping semantic edits need defined order and conflict handling. A hash alone cannot reverse an edit.

The existing [BF16 example](https://github.com/RikiyaT/lm_understand-logs/blob/4d09ba6d6a7e891dd8063974dfe81b3d78e3494f/exp8_math/README.md) and its [source-specific applicator](https://github.com/RikiyaT/lm_understand-logs/blob/4d09ba6d6a7e891dd8063974dfe81b3d78e3494f/exp8_math/code/apply_edit.py) provide a specific indexed replacement precedent, not a general GGUF interchange. See the [research status](research-status.md) for the freshly checked source claims and their limits; results have not been reproduced here. Record actual task outcomes and negative results with model and evaluation context; reconstruction or structural validity does not establish a benefit.
